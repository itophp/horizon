# AI Coding Agent 通用信息化应用基础框架规范

> **用途**：将本文档交给 Codex / Claude Code 等编码
> Agent，作为通用信息化应用的技术架构与工程规范。\
> **目标**：建立一套适合 AI Agent
> 持续生成、修改、测试和维护代码的前后端基础框架。\
> **范围**：只定义通用工程基础设施，不包含任何特定行业、ERP 或业务模块。

------------------------------------------------------------------------

## 1. 给 Agent 的执行要求

开始工作前：

1.  检查当前工作区、Git 状态、现有目录和项目约定，不覆盖或删除已有文件。
2.  阅读本文档，并查阅所选技术的当前官方文档，确认版本与兼容性。
3.  先搭建基础框架与一个通用示例功能，不要自行发明业务模块。
4.  生成文件与手写文件必须有清晰边界；不得直接修改生成目录。
5.  将架构规则、常用命令、代码生成流程和测试要求写入仓库文档。
6.  每完成一个阶段都要运行实际可执行的格式化、静态检查、类型检查、测试和构建命令。
7.  不得通过删除测试、关闭检查、使用
    `any`、吞掉异常或伪造测试结果来让任务通过。
8.  若依赖版本、API
    或工具安装方式无法从官方文档确认，明确记录不确定性，不要猜测。

首轮只完成"基础框架验证"，等待用户确认后再扩展。

## 2. 推荐技术栈

实际开始前，确认当前稳定版本、兼容矩阵，并锁定依赖版本。

### 2.1 前端基础

-   React + TypeScript
-   Vite
-   React Router：路由
-   shadcn/ui：基础 UI 组件，组件源码纳入仓库
-   Tailwind CSS：样式与设计 Tokens
-   TanStack Query：服务端状态与缓存
-   TanStack Table：常规数据表格
-   React Hook Form + Zod：表单与校验
-   **i18next + react-i18next：国际化主方案**
-   `Intl` 原生 API：数字、货币、日期与相对时间格式化
-   Lucide React：图标
-   Vitest：单元测试
-   Playwright：浏览器端到端测试
-   pnpm：包管理

按需引入：

-   Zustand：只管理必要的客户端全局状态，不重复保存服务端数据。
-   AG Grid：只有确实需要复杂电子表格式编辑时才引入。
-   日期库：若项目需要复杂日期运算，可选 date-fns；本地化展示优先结合
    `Intl` 和 i18next，不重复实现日期格式化。

### 2.2 国际化方案决策

**默认选择：i18next + react-i18next。**

选择理由：

-   React 生态成熟，文档和示例丰富。
-   支持命名空间、懒加载、语言切换、插值、复数规则和回退语言。
-   适合中大型应用逐步增加语言。
-   可将界面翻译与日期、数字、货币格式化分开管理。
-   方便 Agent 按固定资源文件结构添加和检查翻译。

备选：

-   **FormatJS / react-intl**：如果团队偏好 ICU MessageFormat，并希望以
    `Intl` 为核心统一处理消息和格式化，可以评估。
-   **Lingui**：如果偏好编译期提取消息和较精简的 React API，可以评估。

不要同时引入 i18next、react-intl、Lingui
多套消息框架。选定一种后全项目统一。

### 2.3 Go 后端基础

-   Go：采用当前稳定版本，固定 `go.mod` 中的版本要求
-   Goa：Design First API 契约与代码生成
-   PostgreSQL：关系型数据库
-   pgx：PostgreSQL 驱动 / 连接能力
-   sqlc：根据 SQL 生成类型安全的 Go 数据访问代码
-   版本化 SQL Migration：选择一个明确维护、兼容 PostgreSQL 的工具
-   Go 标准测试框架：单元测试与集成测试
-   OpenAPI：API 契约
-   Orval：根据 OpenAPI 生成 TypeScript API
    SDK（先验证与生成格式的兼容性）

职责边界：

-   Goa：API 设计、传输层代码和契约生成。
-   sqlc：根据 SQL 生成类型化数据访问代码。
-   应用 / 服务层：实现实际业务逻辑。
-   PostgreSQL：持久化、事务与数据约束。
-   Orval：生成前端请求与类型代码。
-   Agent：编写源代码、测试、调用生成器、定位并修复问题。

Goa 不是完整业务代码生成器。不要将业务逻辑放进自动生成目录。

## 4. 国际化实施规范

### 4.1 语言策略

-   默认语言：英文 `en`。
-   第二语言示例：简体中文 `zh-CN`。
-   统一使用 BCP 47 语言标签。
-   为缺失翻译配置明确的 fallback 语言。
-   用户选择的语言应在刷新后保持；选择适合当前应用的持久化方式，并尊重隐私及安全要求。
-   若用户配置了语言，不能每次都被浏览器语言覆盖。

### 4.2 资源组织

采用命名空间组织翻译，按应用基础、导航、验证和后续功能拆分。不要把所有翻译堆进一个巨型
JSON。

示例：

``` text
i18n/locales/
├── en/
│   ├── common.json
│   ├── navigation.json
│   └── validation.json
└── zh-CN/
    ├── common.json
    ├── navigation.json
    └── validation.json
```

示例资源：

`en/common.json`

``` json
{
  "actions": {
    "save": "Save",
    "cancel": "Cancel",
    "delete": "Delete"
  },
  "states": {
    "loading": "Loading...",
    "empty": "No data found"
  }
}
```

`zh-CN/common.json`

``` json
{
  "actions": {
    "save": "保存",
    "cancel": "取消",
    "delete": "删除"
  },
  "states": {
    "loading": "正在加载...",
    "empty": "没有找到数据"
  }
}
```

以上仅为示例；请使用官方当前版本推荐的 i18next 配置方式。

### 4.3 文案与格式化分离

-   UI 文案、按钮、错误消息和空状态全部通过翻译资源读取。
-   禁止在组件中硬编码面向用户的英文或中文。
-   禁止通过字符串拼接构造句子；使用插值和复数规则。
-   日期、数字、百分比、货币展示使用
    `Intl.DateTimeFormat`、`Intl.NumberFormat` 等
    API，或统一封装的格式化函数。
-   本地化格式化不能改变服务端存储的原始数值。
-   金额精确计算与金额展示必须分离。
-   时区、日期、业务日期与时间点要分别建模，不能仅靠切换 locale 处理。
-   用户可见的服务端错误应使用稳定错误码映射到本地化文案，避免直接显示内部错误细节。
-   表单校验错误应有统一翻译机制。

### 4.4 动态切换与加载

-   提供统一的语言切换入口和 `changeLanguage` 流程。
-   语言切换后更新页面文案与格式化结果，不要求整页重新加载，除非框架或业务确有必要。
-   对大型应用按需加载翻译命名空间。
-   处理缺失 key，开发环境应能发现并报告。
-   在 CI 中检查各语言资源的 key
    一致性，避免新增英文文案后遗漏其他语言。
-   不要把翻译资源中的内容当作 HTML 直接渲染。

### 4.5 国际化测试

至少验证：

-   默认英文语言能正常启动。
-   切换到中文后文案发生变化。
-   缺失翻译按预期回退。
-   插值与复数规则正确。
-   日期、数字和货币根据 locale 格式化。
-   刷新后用户语言偏好仍生效。
-   所有语言资源 key 一致。
-   不存在明显硬编码的用户可见文案。

## 5. 让 AI Agent 更适配项目

### 5.1 根目录 AGENTS.md

创建简明、可执行的根目录 `AGENTS.md`，至少包括：

-   技术栈及版本来源
-   目录职责
-   生成代码边界
-   国际化规范
-   API 契约修改流程
-   SQL / Migration 规则
-   测试和构建命令
-   禁止事项
-   完成任务的汇报格式

需要不同规则的子目录可以增加更具体的
`AGENTS.md`，但不能与根目录规则冲突。

### 5.2 Goa Skill

先查阅 Goa 官方当前的 Coding Agent Skill /
指南，确认安装方式和内容与项目版本匹配。

要求 Skill 指导 Agent：

1.  先读现有设计文件和文档。
2.  修改 Goa DSL，而不是直接改生成文件。
3.  执行代码生成。
4.  在非生成目录实现逻辑。
5.  运行格式化、编译、测试和契约检查。
6.  检查差异，报告破坏性 API 变更。

Skill 是工作流程指引，不是正确性保证。

### 5.3 shadcn/ui 与设计系统

-   配置前先阅读 shadcn/ui 当前官方文档。
-   可用时配置官方 MCP / Registry，帮助 Agent 搜索和安装组件。
-   优先复用项目现有组件。
-   统一颜色、间距、字体、圆角、阴影、焦点状态和响应式规则。
-   不允许每个页面自行建立一套设计体系。
-   公共组件变更前检查所有调用方并运行测试。
-   MCP 返回的组件仍需审核依赖、可访问性、许可证和维护性。

### 5.4 国际化 Skill / 规则

在 `docs/internationalization.md` 中写清：

-   翻译资源命名规范
-   key 命名规则
-   文案提取规则
-   插值、复数、日期和数字格式化方式
-   错误码映射
-   新增文案时需要同步哪些语言
-   CI 如何检测缺失 key

要求 Agent 每次新增 UI 时：

1.  先检查现有翻译 key。
2.  将所有用户可见文案放入资源文件。
3.  为所有已支持语言补齐 key。
4.  执行 i18n key 检查。
5.  编写或更新相关测试。

不要只依赖 Prompt 中"请支持多语言"的一句话。

### 5.5 API / SDK 生成规则

-   OpenAPI / 后端契约是 API 类型的唯一来源。
-   `gen/` 和 `api/generated/` 不手工修改。
-   API 变更后执行生成流程。
-   统一处理认证、错误、超时和重试。
-   不允许页面随意重复声明 API 类型。
-   不允许使用 `any` 规避类型错误。
-   若生成器输出不兼容，先修复配置或模板并记录原因。

### 5.6 MCP 与工具

可按实际需求配置：

-   shadcn 官方 MCP / Registry：查询与安装组件。
-   Playwright：浏览器交互与端到端验证。
-   GitHub MCP：需要时读取 Issue、PR 和审查变更。
-   官方文档查询工具：确认版本和 API。

不要为了"AI 适配"而堆积大量 MCP。优先保证本地
CLI、文档、测试和代码生成流程可靠。生产凭证和生产数据库不能无约束地开放给
Agent。

## 6. 基础安全与工程规则

-   环境变量通过 `.env.example` 文档化，禁止提交真实密钥。
-   对输入执行服务端验证，前端校验不能替代服务端校验。
-   认证与授权必须在后端执行。
-   统一请求 ID、结构化日志和错误处理。
-   明确 CORS、Cookie、Token 和会话策略，不复制未经评估的安全配置。
-   数据库访问使用参数化查询。
-   Migration 必须版本化、可审查。
-   依赖更新需要检查变更日志和兼容性。
-   避免过早微服务化；先建立模块边界。
-   所有外部输入都应被视为不可信数据。

## 7. 质量门禁与生成命令

请在 `package.json` 和 `Makefile` 中定义实际可运行的命令，并写入
README。

前端至少支持：

``` bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

后端至少支持：

``` bash
gofmt -w .
go vet ./...
go test ./...
```

代码生成至少支持：

``` bash
make generate
make check-generated
```

以上是建议命令名，不代表项目初始化后自动存在。请确保命令真实定义且可运行。

CI 至少检查：

-   格式化与 lint
-   TypeScript 类型检查
-   Go 静态检查
-   单元测试
-   构建
-   代码生成一致性
-   国际化资源 key 完整性

不要通过跳过失败步骤来让 CI 通过。

## 10. AI Agent 自动化测试与自动修复体系

本项目必须支持编码 Agent 在本地和 CI 中重复执行测试、读取明确的失败结果、修复源代码并再次验证。测试流程应当可脚本化、确定、可复现，不能依赖 Agent 目测代码或页面截图后自行判断正确性。

### 10.1 推荐测试栈

| 层级 | 工具 | 职责 |
|---|---|---|
| 前端单元测试 | Vitest | 纯函数、状态逻辑、格式化和工具函数 |
| React 组件测试 | React Testing Library + `user-event` | 验证组件的用户可见行为和交互 |
| 浏览器端到端测试 | Playwright | 真实浏览器中的关键用户流程、截图、控制台和网络错误 |
| Go 单元测试 | `go test` | 服务、领域逻辑、边界条件和错误分支 |
| Go Mock（按需） | `go.uber.org/mock` 或手写 Fake | 隔离外部依赖；优先使用小接口和 Fake，避免过度 Mock |
| HTTP / API 测试 | `net/http/httptest` | 验证路由、状态码、响应、错误处理和中间件 |
| 数据库集成测试 | Testcontainers for Go + PostgreSQL | 在真实 PostgreSQL 中验证 SQL、Migration、事务和约束 |
| API 契约检查 | OpenAPI + Orval 生成结果 | 检查后端契约、前端 SDK 和生成流程的一致性 |
| 静态检查 | ESLint、TypeScript、`go vet` | 尽早发现格式、类型和常见静态问题 |
| CI | GitHub Actions 或现有 CI | 在提交 / PR 时运行检查、测试和构建 |

先采用这些工具，不要一开始叠加多个重叠的测试平台。工具版本、安装方式和配置必须以当前官方文档为准。

### 10.2 测试分层原则

**第一层：快速反馈**

每次 Agent 修改后优先运行：

- 前端 lint 与类型检查
- 相关 Vitest 测试
- `gofmt`、`go vet` 和相关 Go 单元测试
- 生成代码一致性检查

这一层应该快，适合 Agent 频繁迭代。

**第二层：集成验证**

在改动 API、数据库、鉴权或生成链路后运行：

- Goa 代码生成
- OpenAPI 生成与 Orval SDK 生成
- Go HTTP 测试
- PostgreSQL Migration 和数据库集成测试
- 服务端与前端之间的契约验证

**第三层：端到端验收**

在功能完成或提交前运行 Playwright：

- 启动真实前后端测试环境
- 使用测试账号登录（如果应用已有认证）
- 完成关键用户流程
- 检查页面、请求、控制台错误
- 保存失败截图、Trace 和必要日志

不要在每次小改动时无差别运行所有慢测试；根据变更范围先运行相关测试，再在阶段完成时运行全量门禁。

### 10.3 Playwright：Agent 的浏览器验证工具

Playwright 应当成为 Agent 验证真实页面行为的主要工具。

要求：

- 使用稳定的 `data-testid` 仅标记难以通过可访问名称稳定定位的元素；优先使用 role、label 和可访问名称定位。
- 测试优先验证用户可见结果，不要过度依赖 CSS 类名或 DOM 内部结构。
- 测试失败时保留截图、Trace、浏览器控制台和相关网络请求信息。
- 对关键流程使用独立测试数据，避免测试之间相互依赖。
- 等待页面的明确状态，不使用随意的固定 sleep 来掩盖竞态。
- 对失败进行重试只能用于识别偶发问题，不能通过无限重试隐藏真实缺陷。
- 对视觉截图使用稳定的测试数据、视口和时区；截图比较不应取代功能断言。

可按当前官方文档评估 Playwright MCP，以便 Agent 直接操作浏览器；同时保留普通 Playwright 测试代码作为可重复执行的验收资产。MCP 用于交互辅助，不应取代自动化测试套件。

### 10.4 Go 与真实数据库测试

- 单元测试尽量不依赖网络或真实外部服务。
- 对 SQL、事务、约束、Migration 和并发行为，使用隔离的真实 PostgreSQL 测试环境。
- 可用 Testcontainers for Go 按需启动测试数据库；CI 环境应明确配置容器运行条件。
- 每个测试使用独立数据库、独立 Schema 或可靠的事务隔离策略。
- 不允许连接生产数据库运行自动化测试。
- 测试数据应可重复创建和清理。
- 对并发、幂等、唯一约束、事务回滚等行为建立明确测试。
- 对生成的 Goa / sqlc 代码，重点验证生成流程、编译结果及其与手写逻辑的集成，不需要为每行生成代码重复编写无意义的单元测试。

### 10.5 API 契约与生成代码检查

定义统一的生成流程，并在 Makefile 中实现真实命令。建议包括：

```bash
make generate
make check-generated
make test
make test-integration
make test-e2e
make ci
```

以上是目标命令名称，不代表它们已经存在。初始化时必须在 Makefile 中定义并验证。

生成流程应当：

1. 从 Goa Design DSL 生成服务端代码和 OpenAPI。
2. 从 OpenAPI 生成前端 SDK。
3. 检查生成器是否产生未预期的差异。
4. 运行 Go 编译、TypeScript 类型检查和相关测试。
5. 禁止手工修改生成目录来修补生成器输出。
6. 若生成结果发生变化，检查源契约和生成器版本，再提交更新。

### 10.6 权限与安全自动化测试

本项目使用 Casbin、RBAC / ABAC 和数据范围控制时，测试必须覆盖：

- 未认证请求不能访问受保护接口。
- 已认证但无操作权限的用户收到预期拒绝响应。
- 用户不能读取其他租户的数据。
- 部门、组织、本人和自定义数据范围正确过滤列表结果。
- 通过详情 ID 直接访问越权记录仍会被拒绝。
- 更新、删除、批量操作不能绕过数据范围检查。
- 字段级敏感信息不会因 DTO 或接口变更意外泄露。
- 权限撤销后，后续请求不应继续沿用失效授权。
- 如果启用 PostgreSQL RLS，测试应使用真实应用数据库角色验证策略；不能仅使用具有绕过 RLS 权限的管理员账号测试。

权限测试必须包含正向与负向用例，并在 CI 中执行。不能只验证前端按钮是否隐藏。

### 10.7 国际化自动化测试

至少自动检查：

- 各语言资源的 key 集合一致。
- 不存在未处理的缺失翻译。
- 默认语言与回退语言行为正确。
- 日期、数字、货币格式化使用正确 locale。
- 插值、复数规则和动态语言切换正确。
- 语言切换后刷新仍保留用户偏好。
- 主要页面没有硬编码的用户可见文案。

可以通过 Node 脚本或测试程序比较翻译 JSON 的 key；不要仅依赖人工检查。

### 10.8 让 Agent 按失败结果自动修复

在 `AGENTS.md` 中要求 Agent 遵循以下循环：

1. 先运行与改动相关的最小测试集。
2. 读取完整错误、堆栈、失败断言和日志。
3. 识别根因，不要直接删除断言或弱化测试。
4. 修改源代码或测试夹具；生成代码问题必须回到源契约或生成器配置修复。
5. 重新运行失败测试。
6. 运行受影响模块的完整测试。
7. 在任务结束前运行项目定义的质量门禁。
8. 汇报实际执行过的命令、通过 / 失败结果、未执行的测试和剩余风险。

设置合理的修复尝试上限，例如同一问题连续三轮仍未解决时，停止自动修改，汇报根因假设和需要人工判断的选项。不要无限循环或通过跳过检查宣称成功。

### 10.9 CI 质量门禁

CI 至少包含：

1. 格式化与 lint
2. TypeScript 类型检查
3. Go 静态检查
4. 前端与后端单元测试
5. 数据库集成测试
6. 代码生成一致性检查
7. 构建
8. 关键 Playwright E2E 测试
9. 国际化 key 完整性检查
10. 权限与安全负向测试

按耗时分层执行：快速检查先跑，数据库和浏览器测试后跑。任何被跳过的测试都必须在 CI 报告中明确显示，不能被误报为通过。

### 10.10 第一阶段测试验收标准

基础框架完成时，至少应满足：

- [ ] 前端单元测试可运行。
- [ ] React Testing Library 能验证一个基础交互。
- [ ] Playwright 能启动应用并验证一个完整的示例流程。
- [ ] Go 单元测试与 HTTP 测试可运行。
- [ ] Testcontainers / 隔离 PostgreSQL 集成测试方案已验证；若环境不支持，记录明确限制。
- [ ] Goa 与 Orval 代码生成流程可重复执行。
- [ ] 国际化 key 检查可自动执行。
- [ ] CI 可运行快速检查与主要测试。
- [ ] 测试失败会返回清晰的退出码与诊断信息。
- [ ] Agent 任务报告会列出真实执行的测试命令及结果。

## 10. 通用权限与数据级授权架构

本节定义通用基础权限设施，不绑定任何行业业务。目标是让 Agent 生成新 API、页面和数据访问代码时，默认遵循统一的认证、操作授权、数据范围过滤和字段保护规则。

### 10.1 推荐方案

第一阶段建议采用：

- **认证**：独立的认证模块，负责验证身份并建立可信的 `Principal` 上下文。具体采用 OIDC/OAuth 2.0、企业 SSO 或应用会话，应按产品需求选择；不要把认证与授权混为一谈。
- **Casbin**：作为 Go 服务端的授权策略引擎，处理 RBAC 角色/操作授权，以及适用场景下的域（租户）和 ABAC 属性条件。
- **RBAC + ABAC**：RBAC 表达“谁能执行什么操作”；ABAC 表达“在什么属性、组织、资源状态或上下文条件下允许操作”。
- **数据访问层强制过滤**：将已解析的数据范围转成 SQL 条件；所有列表、详情、更新和删除路径都必须受保护。
- **PostgreSQL Row-Level Security（RLS，可选纵深防御）**：对多租户或高敏感数据场景，可进一步在数据库层强制行级过滤。
- **OpenFGA（可选备选）**：只有当系统出现复杂的对象共享、资源关系、继承授权等需求时再评估；第一阶段不要同时引入 Casbin 和 OpenFGA。

Casbin 是授权策略引擎，不是完整用户管理系统，也不会自动为 SQL 查询增加数据过滤条件。应用必须把授权决策与数据访问约束连接起来。

### 10.2 权限层级

统一区分以下层级，不得仅靠前端隐藏菜单或按钮实现安全控制：

1. **导航 / 菜单权限**：控制界面展示体验；不是安全边界。
2. **操作权限**：例如 `resource:read`、`resource:create`、`resource:update`、`resource:delete`、`resource:approve`。
3. **数据范围权限**：控制用户可读取或修改哪些记录。
4. **字段级权限**：控制敏感字段是否可以读取或修改；应由后端 DTO / 响应投影和输入字段校验实施。
5. **租户 / 组织隔离**：所有受租户约束的数据必须由服务端强制隔离。

### 10.3 初始数据范围模型

可先支持下列通用范围，具体业务可扩展：

- `ALL`：当前租户范围内的全部记录。
- `ORGANIZATION`：指定组织内的记录。
- `DEPARTMENT`：指定部门及明确授权的下级部门。
- `OWN`：当前用户拥有、创建或负责的记录；“拥有”的定义必须按资源类型明确。
- `CUSTOM`：由明确授权关系指定的组织、部门、用户或资源集合。

数据范围不能只存成一个前端可提交的字符串。服务端应将用户、租户、组织、部门、角色和自定义授权关系解析成可信的 `DataScope`，再由数据访问层应用到查询中。不能信任客户端自行传来的 `tenant_id`、`owner_id` 或 `department_id` 作为授权依据。

### 10.4 建议的 Go 模块边界

```text
services/api/internal/
├── auth/
│   ├── principal.go          # 可信身份与租户上下文类型
│   ├── authentication.go     # 身份验证接口 / 实现
│   └── context.go            # 将 Principal 安全传递给请求上下文
├── authorization/
│   ├── enforcer.go           # Casbin 封装接口
│   ├── action.go             # 标准操作名
│   ├── resource.go           # 资源名与授权模型
│   ├── policy.go             # 策略加载 / 更新
│   └── decision.go           # 统一授权决策
├── dataaccess/
│   ├── scope.go              # DataScope 类型
│   └── scope_resolver.go     # 从 Principal / 策略解析数据范围
├── middleware/
│   ├── authentication.go
│   └── authorization.go
└── repository/
    └── ...                   # 查询必须应用数据范围
```

上述是建议的模块边界，实际文件可随项目调整。业务 Handler 不应自行复制权限判断逻辑；统一通过明确的接口和中间件 / 服务层进行授权，并在 Repository / 查询层实施记录范围约束。

### 10.5 请求处理流程

对每个受保护请求，按以下流程实施：

1. 验证身份，建立可信的 `Principal`，包含用户 ID、租户 ID，以及按需解析的组织 / 角色信息。
2. 校验请求参数和资源标识。
3. 检查该主体是否具有对应资源和操作的权限，例如 `document:read`。
4. 解析适用的数据范围，并应用到数据库查询。
5. 对详情、更新、删除等单记录操作，在查询 / 修改时同时校验资源是否位于授权范围内，避免先无约束读取再检查。
6. 对敏感字段执行后端字段级读取 / 修改控制。
7. 记录必要的审计事件，但不要在日志中泄露令牌、密码或不必要的敏感数据。

未授权默认拒绝。若策略服务或上下文解析失败，不能悄悄退化为全量访问。

### 10.6 数据访问规则

- 所有租户数据访问都必须带有可信的租户约束；不能由客户端参数决定当前租户。
- 列表查询必须在数据库查询层应用范围过滤，不要取出所有记录后再由 Go 代码逐条过滤。
- 详情、更新和删除必须验证目标记录处于授权范围内；对更新 / 删除优先使用带范围条件的原子查询。
- 对关联查询、聚合、导出、后台任务、批量操作和文件下载应用同等授权规则，不能只保护普通列表 API。
- 对自定义范围使用参数化 SQL 或类型安全的查询构建方式，禁止拼接不可信 SQL 字符串。
- 角色 / 策略缓存必须定义失效策略，避免权限撤销后旧缓存持续生效。
- 授权失败时统一返回适当的错误；不要向调用者泄露其无权访问资源是否存在等敏感信息（按产品安全策略决定 403 / 404）。

### 10.7 PostgreSQL RLS 规则（按需启用）

RLS 可作为额外防线，但不能代替应用层的身份验证、操作授权和审计。

若启用 RLS：

- 为相关表显式定义策略，并测试 SELECT、INSERT、UPDATE、DELETE 行为。
- 应用数据库账号不得拥有绕过 RLS 的权限；注意表所有者、超级用户和 `BYPASSRLS` 等特殊角色的行为。
- 使用连接池时，在事务内安全设置租户 / 用户上下文，并确保事务结束后上下文不会泄漏到复用连接。
- 覆盖后台任务、迁移脚本、报表、导出和批量操作的访问策略。
- 增加跨租户访问的负向集成测试。

不要为了“看起来安全”而在未理解连接池和数据库角色行为时机械添加 RLS；应通过测试验证实际隔离效果。

### 10.8 Agent 生成代码的强制规则

将以下要求加入根目录 `AGENTS.md`：

- 新增受保护 API 时，必须声明资源、操作和所需数据范围。
- 所有受保护 API 必须执行服务端认证和授权。
- 前端菜单、按钮和路由守卫只改善体验，不构成安全边界。
- 所有列表、详情、更新、删除、导出和批量操作都必须执行数据范围检查。
- 禁止信任客户端传来的租户 / 组织 / 所有者字段来决定授权范围。
- 禁止直接修改 Casbin 生成 / 加载策略的约定文件之外的隐式权限规则；策略格式和变更流程必须有文档与测试。
- 不允许在每个 Handler 里复制不同的权限逻辑；使用统一授权接口和数据范围解析器。
- 新增字段时评估字段级读取与修改权限，尤其是个人信息、凭证、成本、金额和内部备注等敏感字段。
- 新增或修改权限时，必须补充允许与拒绝两类测试。
- 任何授权失败、策略加载失败或数据范围解析失败，都不得默认放行。

### 10.9 必须具备的权限测试

至少覆盖：

- 未登录用户无法访问受保护 API。
- 已登录但无操作权限的用户被拒绝。
- 用户只能读取授权数据范围内的记录。
- 通过直接请求详情 ID 不能绕过数据范围。
- 用户不能更新或删除范围外记录。
- 跨租户读取、更新、删除均失败。
- 列表、导出、批量操作和关联查询不会泄漏范围外数据。
- 敏感字段不会通过响应 DTO、日志或导出意外泄露。
- 权限撤销后缓存会按设计失效。
- 若启用 RLS，验证不同租户上下文和连接池复用时不会串租户。

### 10.10 第一阶段实现范围

基础框架阶段先搭建可扩展的权限接口与最小验证，不必创建完整的可视化权限管理后台：

1. 定义 `Principal`、资源、操作、授权接口和 `DataScope` 类型。
2. 接入 Casbin，定义最小 RBAC 策略示例。
3. 创建一个演示资源 / 演示 API，验证操作授权和数据范围过滤。
4. 编写允许 / 拒绝测试与跨租户负向测试。
5. 记录策略存储、角色管理 UI、策略缓存、审计及 RLS 是否启用的后续决策。

只有在基础授权流程通过测试后，再扩展角色管理界面、权限矩阵、用户授权配置和自定义数据范围管理。
