# ADR 004：账号多部门与部门独立授权

状态：已实施，验证结果见 docs/verification.md。本决策扩展 ADR 002 的单部门模型与 ADR 003 的临时权限绑定。

## 授权语义

一个账号可属于同一租户内多个公司的多个部门，最多 50 个部门。每个部门分别配置角色和账号权限覆盖；角色继承、覆盖替换、显式 deny、六种数据范围保持现行规则。主部门是默认登录上下文，其余部门是附加归属；不同部门的权限不合并。用户通过侧栏“当前部门”切换，服务端验证归属与公司/企业/部门启用状态后，按当前部门计算 Principal、正式角色、独立覆盖、范围及临时权限。客户端传入的部门 ID 只作为待验证选择，不能直接成为身份。

主部门停用但存在其他启用归属时登录选择首个启用部门；当前会话的明确部门被移除或停用后拒绝请求，重新登录可选择仍启用的归属。内置管理员全权绑定受保护主部门，不能通过移动主部门复制或丢失管理员锚点。

## 持久化与兼容性

00004 追加 iam_department_memberships / iam_department_membership_roles，复合外键确保账号、公司、部门、角色同租户及公司部门一致性。原 iam_accounts / iam_account_roles 保留主部门数据，不重写已应用迁移。AccountRecord.memberships 返回主部门及附加归属；原 organizationId/departmentId/roleIds/overrides 是主部门配置，在 SessionProfile.account 中投影为当前部门配置，activeDepartmentId 明确当前上下文。membership.departmentName 为服务端展示字段，写入忽略。

Create/UpdateAccount 的可选 departmentAccess 对象表示显式替换附加部门；对象内 memberships=[] 表示移除全部附加部门，省略对象保留附加归属。主部门仍由原字段配置。账号信息、主部门角色、附加部门及角色写入共用一个事务；重复部门、公司不匹配、跨租户和不存在角色均拒绝。

## 安全边界

- 列表、详情、修改和删除在 SQL 中按可信租户与任意归属部门匹配账号；部门成员统计按所有归属计算，角色成员去重。
- 归属增删及其角色/覆盖修改属于持久授权变更，必须有独立 access:manage 和正式 accounts:create/update，且正式范围覆盖所有原有及目标部门。不能借 OWN、临时写权限或单一部门权限改写另一部门的授权。移除已停用的旧归属仍需正式范围覆盖，但不要求旧部门启用；新增归属必须启用且公司部门匹配。
- 多部门账号的全局敏感信息、凭证、主部门配置和删除也要求正式范围覆盖所有归属。普通业务字段仍遵守既有操作和 SQL 范围。
- 切换 POST /api/auth/department 需要已有会话、Origin 和 CSRF，轮换 CSRF，不延长会话有效期。所有请求重新读取部门策略，撤权即时生效。前端取消旧请求、清除私有 Query 缓存并重建部门界面，不能沿用前一部门数据。
- 临时申请记录可信 department_id，审批按照该部门申请人的覆盖策略和相对范围解析；审批人仍受自己当前部门的正式权限上限约束。临时授权只在申请部门生效，保留原始申请、批准和部门信息。移除归属会取消待审/撤销已批准请求，再次加入不会复活旧授权。

## 规则同步与验证

任何权限控制变更都必须同步 baseline-security、受影响目录 AGENTS.md 与 docs/security.md / 决策规则；涉及前端、数据库时同步相应 Skill 的操作约束。不得只改实现。覆盖部门角色隔离、独立 allow/deny、六种范围、范围内成员可见性、非法切换、CSRF 轮换、跨租户/公司不一致、持久授权边界、撤权与临时权限上下文，并执行 make test-security 与 make ci。

Down 会删除附加部门配置与上下文列，只用于隔离迁移验证；真实部署回滚需先导出新配置并评估数据丢失，不自动执行。


内置管理员账号仍禁止停用、删除及移动受保护主部门；界面中主部门策略的锁定不能连带隐藏本人添加附加部门的入口。附加部门仍独立配置角色/覆盖，遵守既有正式权限与范围校验。其他账号不能编辑内置管理员，详情模式及无部门授权管理权限时，部门策略控件保持只读。 前端把“可管理归属”与“可编辑当前部门策略”分开判断；主部门的内置全权保持不可配置，选择附加部门后才开放该部门策略。
